# 产品定位与展示原则

TokenFlow 是本地模型网关：集中管理来源账号和 API，把所选模型接入用户已有的 Agent，并提供配置备份、恢复和实际用量记录。主要操作围绕账号、来源、模型和客户端展开，内部路由细节由程序处理。

文档入口见 [项目文档](README.md)，实现职责见 [项目架构](architecture.md)，未完成事项统一记录在 [TODO](TODO.md)。本页记录产品要求，不代表所有客户端已经实现或验收通过。

## 模型名称：对外显示可读名称

模型的可读名称与内部模型 ID 分开管理。TokenFlow 界面和导入目标客户端后的模型菜单，默认显示可读名称；不将原始模型 ID 拼接到名称后面，也不重复显示来源前缀。

| 场景 | 展示要求 |
| --- | --- |
| 单个模型 | `GLM-5.3-Flash` |
| 需要区分来源 | `Qoder · GLM-5.3-Flash`；如果沿用来源前缀样式，也只能出现一次 |
| 禁止出现的重复形式 | `qoder/GLM-5.3-Flash:qoder/gfmodel` |
| WorkBuddy 截图中的同类问题 | `codex/GPT-5.6-Luna:codex/gpt-5.6-luna`，名称后又带出内部 ID |

这条规则适用于 TokenFlow 内的模型卡片、选择器，以及导入 WorkBuddy、Qoder、Codex、Claude Code 等客户端后的可见菜单。不能只修 TokenFlow 自己的显示，而让目标客户端继续出现“名称:内部 ID”。

### 名称和请求标识的边界

- 导出配置时分别处理显示名称和协议所需的请求标识；内部 ID 可用于路由、来源绑定和权限检查，不作为用户默认可见的模型名称。
- 重命名仅影响显示，不改变来源账号、调用模型、Key 授权或历史用量归属。
- 同名模型需要区分时，显示来源／账号标签；不要用原始路由 ID 充当名称后缀。
- 在明确的接口接入、复制请求 ID 或诊断详情中，可以按需提供精确模型 ID；普通模型菜单和导入结果不默认附带它。
- 如果目标客户端自行把名称和 ID 拼接展示，需要在该客户端适配层处理可见标识与内部路由的映射，不能只靠修改显示名称掩盖问题，也不能删掉协议必需字段导致调用失败。
