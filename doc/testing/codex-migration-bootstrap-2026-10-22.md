# Codex 按历史迁入整理与用量分离（2026-10-22）

延续 `47a1db1` 的摘要合并和具体错误传递修复。本次落实用户确认的边界：新对话由 Codex 决定压缩，来源切换只备份和改路由；旧对话迁入后的首次实际续聊才可能整理未覆盖的历史。没有新增截断、请求上限、等待时限或失败冷却。

## 行为

- `CodexThreadMigration` 从已有切换备份提供“对话/分支 ID、官方历史版本、记录时间”。网关新建的对话没有这条迁入证据，不因为输入很大、换模型、换 Key 或重启而主动整理。读取的是缓存的备份元数据，不在每次推理时扫描全部对话。
- 首次整理前仍先复用当前分支匹配的历史前缀。原来的 256 KiB 整理目标仅衡量尚未覆盖的旧消息，排除固定指令、已有摘要和当前用户请求；不会因大段固定指令生成空检查点。这个目标只适用于有迁入记录的旧对话，不是新对话的压缩阈值或请求拒绝上限。
- 整理完成后保存已处理的历史版本，替代用连接 ID 判断“首次”。再次从官方带回新增历史会有新的版本；相同历史换凭据不再触发首次整理。失败前完成的分块继续复用，失败不会把未完成的整理标为已完成。
- 原有 `managed-session-v1` 升级为 v2 时，结合迁入记录时间与已保存状态时间识别升级前已经处理的导入，避免仅因升级多整理一次；这不是等待计时或超时策略。
- 来源快照和备份用于恢复，不覆盖当前活跃对话。A → 网关 B → 官方 C → 网关继续使用最新历史。前缀匹配不允许较晚分支的摘要混入回退后的另一条分支。官方不能直接解读网关密文时，仍按原流程还原最新文字检查点并保留它之后的新消息。

## 用量

首次整理内部的摘要调用消耗通过独立回调交给 TokenFlow 记账和活动统计；返回给 Codex 的普通续聊响应只包含该次续聊模型实际报告的输入、缓存和输出用量。

例如摘要消耗输入 100 / 输出 10，续聊输入 7 / 输出 3：Codex 收到 7 / 3；TokenFlow 记账输入 107 / 输出 13，活动保留摘要明细 100 / 10。流式、非流式，以及摘要完成后续聊失败的记账都有覆盖。显式远程压缩自身的实际调用消耗仍正常记录，不伪造为零。

## 验证与边界

- 四个新回归在修改前全部失败，分别覆盖网关新会话、大固定指令、凭据变更/新增官方历史和用量混合。旧代码中续聊实际输入 100 Token，却把三次摘要加进去返回 1500100 Token；修改后返回 100，记账保留总消耗。
- 补充历史分支回退、旧状态升级、迁移元数据跨重启、流式/非流式独立记账验证。更新了一条仍假定“后续压缩永远保留全部旧摘要”的旧断言，改为检查旧摘要进入合并输入、输出只保留新的有效摘要。
- 安装版 Codex、合成来源、隔离 HOME：连续完成官方 → 网关 → 官方 → 网关 → 官方，断言最新网关回复和随后官方新消息均存在；网关期间连续完成三次客户端触发压缩，工具结果和最新约束保留。
- 安装版 Codex、12,666,535 字节合成历史：切换时压缩 0 次，首次实际续聊整理 1 次，重启续聊复用。夹具故意把摘要累计输入报为 8800 万 Token；Codex 看到的当前输入保持 100 Token，没有因此额外触发压缩。约 4 秒的测试耗时是本地合成来源速度，不是真实 Luna 性能。
- 原生检查点与错误回归继续通过：24 次续聊、3 次压缩始终只有一份当前合并摘要，Qoder 429 的“选择其他模型”提示到达 Codex。
- 17 个相关套件共 252 个用例完成验证，另有 3 个 API 错误传递集成用例通过。集中运行初次为 249 通过 / 3 失败：两条旧用量断言按新的“客户端用量 / 记账用量”分别断言后，所在文件 26 项全部通过；另一次失败发生在测试 sidecar 启动健康检查，原用例不改时限单独重跑通过。没有把这一轮描述成集中运行一次全绿。类型检查、构建通过。
