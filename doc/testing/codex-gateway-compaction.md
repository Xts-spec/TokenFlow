# Codex 网关长会话压缩

## 官方会话首次切换（2026-10-22 当前行为）

切换时只备份会话、迁移来源，不调用压缩接口或摘要模型，不扫描所有旧对话来安排摘要任务。首次全备份与后续增量备份保持原有机制，已有摘要记录继续保留。

实际续聊某个托管 Codex 对话时，网关根据 `session_id`（兼容 `session-id`）只读取该对话的摘要记录。先恢复检查点、匹配已覆盖的历史前缀；该接入的首次请求中，剩余历史超过已有客户端软预算的字节估算（65536 × 4）才分块整理。当前请求内生成摘要并继续正式回答，不启动第二个 Codex 进程操作正在使用的 rollout。短历史直接转发；没有会话标识的普通接口请求不猜测对话归属。

首次整理是接入兼容处理，不是每轮自动压缩。成功后保存当前接入已处理状态；摘要失败不记完成、不设置冷却，下次请求复用成功分块并继续。正式回答失败时已生成的摘要仍保留。切换来源再回来时，先复用旧摘要，只整理尚未覆盖且需要处理的历史，不重做完整摘要。

后续由 Codex 根据整个上下文的用量决定何时发出远程压缩请求，网关执行 `/responses/compact`、`compaction_trigger` 或显式 `context_management`。接入配置使用 `model_auto_compact_token_limit_scope = "total"`，模型目录保留 65536 Token 的客户端软触发值。当前运行时按 provider 的 `name = "OpenAI"` 选择远程压缩；来源键仍为 `token_flow`，请求仍发给所选网关模型。这些软目标不产生新增请求拦截。

官方的 `compaction.encrypted_content` 不是其他模型可读的摘要。TokenFlow 只在托管的 Codex 接入中，从本机 rollout 找到匹配的压缩条目，恢复它覆盖的可读历史，再生成网关检查点。不会把官方密文当作正文，也不会修改原始 rollout。

rollout 文件大小不等于请求 Token 数：文件还包含事件、用量和重复记录。验证样本为本项目的一份 12,277,233 字节 rollout，恢复后的请求历史约 4.7 MB。普通导出 Key 不能调用这条本机恢复路径。

恢复扫描不按 rollout 文件大小或可恢复历史字节数跳过会话。仍须匹配准确的检查点；找不到明确历史时要求提供可读交接摘要，不会猜测官方密文内容。

## 压缩策略与预算

- 摘要使用当前授权来源和模型，读取 Responses SSE；正文可来自完整终态、完成条目或文本增量。推理增量只表示进度，不作为摘要正文；缺少终态、空正文、工具调用或未完成摘要均拒绝替换历史。
- 旧工具参数、工具结果和助手工作保留有明确省略标记的摘录。工具结果兼容字符串和内容数组；旧二进制附件只保留占位说明。较早的用户文字提供给摘要模型；当前用户消息、指令以及最近完整工具交换原样保留，已经原样保留的内容不再重复进入摘要。省略内容需要时回看原会话或重新读取文件。
- 摘要按最多 48 KiB UTF-8 文本分块，按需要完成全部分块。有效摘要允许比摘录或原输入更长，不因字节比较返回 422。压缩结果按 **JSON 序列化后的真实大小** 判断是否值得继续归并；归并不再缩小时保留已有有效摘要并继续续聊，不反复调用模型。不再因预计或实际摘要调用超过 32 次而中断。
- 历史缩减基准为 128 KiB；实际目标至少容纳固定工具定义、系统/开发者指令、最新用户消息和最近完整工具交换，并保留 32 KiB 历史空间。它用于首次续聊的兼容整理及客户端明确请求的压缩，不是模型窗口或请求字节上限。固定内容大时不由网关额外返回 413。
- 模型目录不声明较小的 `context_window`：桌面运行时可能在窗口缩小时先用旧模型压缩，导致旧官方模型被发到新网关。首次续聊在当前请求内处理不可靠的旧用量；后续按客户端整个上下文的用量触发。
- 上游真实 `context_too_large` / `context_length_exceeded` 在 HTTP JSON 和 SSE 错误中统一成 Codex 可识别的 `context_length_exceeded`，SSE 使用 `response.failed`。不把网络、额度或其他错误误报为超限，也不在错误后由网关另起摘要循环。非托管接入的旧会话仍可能需要用户在 Codex 手动压缩；错误归一化本身不保证所有客户端会自动重试压缩。
- 通用生成请求没有网关的空闲计时或单请求总时限，摘要工作请求也不再设置 300/600 秒计时。Node HTTP 生成调用显式关闭响应头和正文的默认等待计时，同时沿用当前网络代理。上游响应、断流、客户端取消仍正常传递；WorkBuddy 等来源适配器自身的计时另见[等待策略核查](gateway-waiting-policy-2026-10-21.md)。

## 失败、复用与用量

空摘要、未完成、工具调用等无有效交接正文的响应仍返回具体 `compaction_*` 错误，原历史保留。所有失败均不缓存、不设置摘要重试冷却；下一次请求立即重新尝试失败部分。并发请求只共享仍在执行的摘要调用，已完成的有效摘要继续缓存复用。摘要长度没有缩短本身不属于失败。

托管 Codex 的已完成摘要块和对话摘要记录使用本机密钥加密保存，不随临时缓存的 7 天或 512 块清理删除。摘要记录按对话隔离，使用已覆盖历史前缀的指纹匹配；切换 Key、来源或模型后可以复用同一对话的已完成摘要。中途失败时已成功的分块也保留，重试只生成缺失部分；已有摘要原样保留，新增历史单独摘要。上游 `store:false` 不影响这些本机记录。

普通导出 Key 的摘要缓存仍按 Key、来源、模型隔离：`store:false` 只在内存复用，其他临时持久缓存保留约 512 块、7 天。摘要记录复用不计为新的上游调用，也不等同于模型的输入缓存命中。

正式回答失败或流中断时，仍结算已经确认的摘要消耗。缺失部分用量标记为未结算，保留确认部分作为下界；未知缓存不记成零。Responses 聚合用量中的 `token_flow_unmetered:true` 表示仍有未报告部分。调用详情展示压缩大小、调用/复用块数、耗时及输入、输出、缓存、推理 Token；摘要用量已计入请求总量，不能重复相加。

## 续聊与切回官方

不增加摘要正文展示或额外正文查看记录。安装版 Codex 主动压缩时，已验证会发送 `item/started`、`item/completed`，条目类型为 `contextCompaction`；沿用客户端原生状态。网关首次接手历史时的内部压缩暂不增加自定义进度事件或额外聊天回复。

网关继续多轮时，会展开最近检查点并追加后续消息，等待 Codex 请求下一次压缩。请求到来时，已有摘要原样保留，只摘要尚未覆盖的较早消息。当前指令、最新用户消息和最近完整工具交换继续保留；不会每一轮重新扫描和发送全部原始 rollout。恢复后来生成的官方检查点时，也沿用其中此前已有的网关摘要，而不是重新拼回被摘要替代的原文。

早于近期窗口的用户消息统一进入摘要，不再因为原文较短而额外保留一份。正式上游请求由可读摘要、近期消息（含完整工具交换）、最新用户请求、指令和本次工具定义组成。客户端重放已被摘要覆盖的旧用户消息时，不会将其重新拼回上下文；检查点之后明确重发的消息仍视为新请求。完整本机历史不因此删除。该整理不增加请求大小或摘要调用次数拦截。

从 TokenFlow 切回官方前，若需要改写会话则必须退出 Codex。程序会先备份，再将最新 TokenFlow 加密检查点展开成可读摘要和近期上下文、清理网关生成的异源条目标识，保留检查点之后的消息和工具配对；切换本身不调用摘要模型。切回官方后并不会恢复已经在摘要中省略的旧正文，需要时仍应回看原会话备份。后续压缩由官方 Codex 链路负责。

## 首次备份与后续增量

首次处理的对话保留完整基线，之后以 `codex-history-backups` 中的内容版本和字节差异记录追加或兼容改写，原始基线不被覆盖。旧版已有的完整备份直接作为基线引用。迁移与切回官方的兼容改写共用这份历史存储，未变化内容不重复复制；新增对话建立自己的完整基线。数据库恢复基线同样复用，历史投影可以从会话记录重建。

切换记录保留当时观察到的来源、模型和可恢复历史版本。当前对话仍跟随官方／网关切换；保留网关来源记录不代表切回官方后仍使用网关。重复检查已完成的路由不重新调用迁移运行时，切换也不会将旧备份覆盖到当前对话。

2026-10-21 回归：实际安装的 Codex 运行时配合隔离的合成来源完成 50 次请求、3 次网关阶段客户端压缩生命周期及多轮官方／网关切换；确认 `session_id` 对应实际对话 ID，普通后续请求没有偷偷产生摘要调用。合成测试还覆盖摘要跨模型／重启复用、部分失败后的分块续做、增量历史精确还原，以及来源切换后新增对话。没有消耗真实来源额度，此验证不代表真实厂商网络问题已经解决。

## 授权与网络错误的区分

- `model_not_allowed`（403）在模型调用前发生，表示客户端请求的模型 ID 不在该 Key 的授权列表。不能只据此断定用户选错模型：Codex 的切换前压缩也可能沿用旧模型。须对照模型选择事件与实际请求；不能用更改 DNS 或重新登录修复模型列表不匹配，也不能静默改投其他模型。
- `compaction_upstream_failed`（422）表示摘要调用的上游返回错误。保留 HTTP 状态和经过白名单分类的原因；不透传原始上游正文。HTTP 500 本身不能证明是网络、额度或模型参数问题。首次摘要失败时不会替换原始历史。
- 授权链接生成超时不能直接判断 Local Agent 进程停止；若本机网关已返回 HTTP 错误，提示明确区分网关响应与厂商授权失败。
- 网络检查分别探测本机网关、应用出站、网关出站，并分别覆盖 WorkBuddy 国内版 `copilot.tencent.com` 和国际版 `www.workbuddy.ai`。只访问固定公开端点，不携带账号凭据或调用模型。
- 出站遵循环境代理或系统代理/PAC；未配置时直连。TUN 和 fake-ip DNS 可在操作系统层接管直连流量，应用显示“直连”并不证明底层未经过代理。安装包不包含开发者的代理节点或 DNS 配置。
- 其他电脑报错时，在“设置 → 检查网络”后“复制诊断信息”，核对版本、网关状态、各目标的两条出站链路及最近路由。公开网站收到 HTTP 响应只证明当时链路可达，不保证登录、API 调用或持续连接成功。

### 2026-10-21 续聊 413 与摘要后的 503
