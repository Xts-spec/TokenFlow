# 网关限制核查与续聊修复（2026-10-21）

## 5 分钟的来源

上一轮 Qoder 测试的 `idle timeout waiting for SSE` 来自 Codex 客户端，默认 `stream_idle_timeout_ms = 300000`，接入配置没有写入此值。官方配置文档：[Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference)。网关自身也有 300 秒无上游数据计时，两者数值相同但作用层级不同；不能因此宣称网关没有时间限制。

首次整理以前只发 SSE 注释，客户端仍会等待有效事件。本次改为每 15 秒发送真实的 `response.in_progress` 状态，不输出助手文字、不伪造 token 或成功结果。拿到正式上游响应后停止首次整理的状态事件。取消、失败仍传回客户端。未写入一个更长的 Codex 超时。

原生安装版 Codex 的可重复验证：上游合成摘要延迟 35 秒、客户端 SSE 等待 20 秒、重连次数设为 0。旧注释心跳失败，新进度事件在 35.102 秒完成回答并保留最早任务标记。该耗时是故障验证的合成延迟，不能当作真实 Luna/Qoder 性能。

## zstd 与稳定分组

支持客户端继续发送 zstd，不关闭其压缩功能。正式本机与 LAN 网关共用 `gatewayDecoding`，在 JSON 解析前流式解压，向 Fastify 提供实际收到的编码字节数，以正确验证压缩后的 Content-Length。无效 zstd 返回格式错误，不产生模型请求。解压后 33 MiB 的 LAN 请求通过；本机 2 MiB Unicode 请求与原始 JSON 完全一致。

首次按容量和时间权重规划后，在模型调用前保存加密分组清单。清单按管理会话保存，不跟随连接轮换。组内容去重存储，并保留历史布局；临时缩短或回退后再恢复，也不会删除原来布局。消息逐条序列化，追加消息不会改变前一组的数组闭合标记；原组文本、细节权重保持稳定，追加内容归入新组。编辑时对齐仍存在的原组，变化部分重新规划，原文不丢失；摘要缓存按实际文本验证，不能把旧事实误用为编辑后的摘要。合并层的输入变化时仍需合并，以纳入新事实。

只有首次整理套用这套规划。后续普通增长仍不由网关自动触发；由 Codex 发起的后续压缩保持既有串行策略。新清单兼容原有有效检查点和摘要恢复，但旧版本中未保存清单的未完成压缩，需要首次建立清单；不能声称以前所有未完成块都能按新格式命中。

模型切换后优先复用已有摘要；缺失组若超出接收模型容量，由真实上游容量错误触发细分，不加本地拒绝或文本截断。Luna 和 Qoder 使用同一实现；上一轮 Luna 从官方模型缓存读到 272000 上下文，Qoder 未从当时的 /models 读到容量，使用未知容量的 512 KiB 起步规划。这个差异影响分组，不改变并行/时间权重策略。

## 与生成调用有关的剩余限制

| 位置 | 本次修复后的行为 | 性质 |
|---|---|---|
| 网关生成请求正文 | 本机/LAN 的生成路由采用 Number.MAX_SAFE_INTEGER，无应用设定的实用字节上限；不截断 | 仍受运行时内存和上游真实窗口约束 |
| API 私有中转 | 移除原有 16 MiB 请求体和单 SSE 事件拒绝；17 MiB 请求与响应事件完整通过；移除其 30 秒上传时限 | 与其他生成入口保持一致 |
| 网关实际上游请求 | 300 秒无数据、600 秒单请求总时限仍存在 | 本地旧超时，确实可能终止慢请求；本次未擅自调整 |
| 首次多块整理 | 整个任务不套 600 秒累计上限，每个上游工作请求独立计时；有效 SSE 状态保活 | 四路并行；Cursor 因 SDK 单账号并发限制排队 |
| Codex 客户端 | 默认 SSE 等待 300 秒、流重连 5 次；接入配置未覆盖 | 官方默认，非本次新加 |
| Codex 目录 | 仍声明 auto_compact_token_limit=65536 | 本地早期写入的软触发值，不是模型容量或拒绝上限；可能导致频繁压缩，本次未改 |
| 首次启动目标 | 未覆盖历史超过约 256 KiB 时整理当前管理会话 | 首次整理触发目标，不是请求拒绝 |
| 压缩保留与合并 | 约 128 KiB 窗口目标会随固定指令、工具和当前请求扩展；16 KiB 摘要合并目标只决定是否继续合并 | 不裁剪或拒绝超目标摘要；不能缩小则保留有效结果 |
| 后续显式压缩 | 48 KiB 串行摘要分块，保留当前用户指令及完整工具交换 | 仅 Codex 请求后执行，无 1 KiB 摘录或摘要输出 token 上限 |
| WorkBuddy SDK 路线 | 本地 240 秒总时限；运行时 60 秒无模型进展检测，允许一次未暴露输出的重试；maxTurns=1 | 确实存在的本地适配策略，不应归为上游业务配额；未改 |
| Cursor/WorkBuddy 工具格式 | 适配器最多 2048 个工具/命名空间内工具，名称最多 128 字符，只支持其可执行的客户端工具类型 | 协议适配校验，未加聊天文本大小限制；未改 |
| sidecar SSE 行缓冲 | Qoder/WorkBuddy/Trae/Doubao 原有单行 1 MiB，部分原生/API 路线 50 MiB；Kimi 依路线不同 | sidecar 传输实现边界，超大单事件仍可能失败；未改 |
| 客户端 Key | 额度默认无限；用户配置额度、模型/账号范围、停用状态、LAN/IP 范围仍生效 | 已有产品权限，不随本次修复扩大或取消 |
| 摘要结果校验 | 空摘要、不完整响应、误调工具仍报来源/协议错误，并保留原记录 | 不能把模型未成功的结果标成成功检查点 |

没有恢复 1 KiB 摘录、工具输出 10000 字节截断、摘要 8192 Token 上限或“摘要必须缩小”的拒绝。二进制历史附件仍按文本摘要原策略用占位引用，不把二进制解码成正文。运行日志的工具名称/条数裁剪只影响诊断展示，不改模型输入。

管理/元数据还有独立格式边界：普通管理路由的默认 JSON 大小、遥测 1 MiB、API 模型列表 16 MiB/15 秒/2000 个条目、账号或字段长度限制，以及授权/网络地址检查、配置路径含符号链接时的改写拒绝；这些不是聊天历史的生成字节限制。普通非管理摘要缓存保留最多 512 份/7 天，内存摘要最多 256 份；管理会话摘要、检查点和本次分组清单不按此规则到期删除。
