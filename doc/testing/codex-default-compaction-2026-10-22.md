# 取消 65536 软阈值的兼容性核验（2026-10-22）

用户后续澄清允许保留合理的自动压缩触发，目标是避免频繁压缩；同时删除 WorkBuddy 本地计时。本页保留“完全删除阈值”的实验状态，最终实施见[模型等待与压缩策略](gateway-model-policy-2026-10-22.md)，原澄清已解决。

## 状态

按用户要求准备删除 `codexModelCatalog` 中写死的 `auto_compact_token_limit=65536`。现有首次接手历史的 256 KiB 整理目标单独命名，数值与行为不变，不再依赖模型目录中的 Token 常量；它不是请求拒绝或后续每轮压缩阈值。

源码候选和证据已保存，**未打包替换运行版**。当前运行版仍为 10.15.26.50；真实用户的 Codex 配置与已生成目录未改。原因是实测发现仅删除阈值会使当前 Codex 在容量未知的自定义模型上失去自动压缩，需要用户明确这类模型的处理方式。异步询问已发出：先补真实容量并验证，或直接删除并接受手动压缩。不能把未回复视为同意某一种行为。

## 原生 Codex 的实测结果

使用安装版 `codex-cli 0.163.0-alpha.11`，临时 HOME/CODEX_HOME 与合成本机来源，不调用真实模型，也不修改真实账号。

| 场景 | 结果 |
| --- | --- |
| 目录不含窗口或 65536，连续 6 次小工具调用，每次报告 140000 输入 Token | 完成，自动压缩 0 次，`modelContextWindow=null` |
| 无容量的模型，切换后连续报告 300000 输入 Token | 续聊完成，自动压缩 0 次；显式 `thread/compact/start` 成功，随后续聊及切回原来源成功，最早标记保留 |
| 无容量的模型，客户端首次重放约 532 KB 历史，合成来源返回真实格式 `context_length_exceeded` HTTP 400 | Codex 回合失败，没有自动压缩或重试；不能依赖该错误码自动兜底 |
| 只在隔离测试目录声明 272000 窗口，不声明自动压缩阈值 | 3 次原生自动压缩及续聊成功；新对话与恢复原来源通过 |
| 测试目录声明 131072 小窗口 | 重现原有切换前沿用旧模型发起压缩的 403；不能仅添加较小窗口就宣称所有切换问题已解决 |

272000 来自本机官方模型缓存中 `gpt-6-luna` 的容量条目；它在上述测试中只用于已知容量实验，没有写入生产模型目录。当前 sidecar `/v1/models` 检查的 52 个 Codex/Qoder/WorkBuddy 模型（其中 15 个 Qoder）均未提供 `context_window` 或 `context_length`。这说明现有可读元数据缺字段，不证明厂商没有定义真实容量，也不能据此随意猜一个窗口值。

[OpenAI Docs 配置示例](https://learn.chatgpt.com/docs/config-file/config-sample)说明未设置自动压缩阈值时使用模型默认值；实际自定义目录若同时缺少容量，安装版返回窗口未知，上述实验验证了这个边界。

## 保留日志核查与第 2、3 项的解释

只读检查当前 `gateway-traces.json` 保留的 1000 条记录，时间范围为 UTC 2026-10-21 12:20:03 至 2026-10-22 07:04:06。日志有保留上限，不能把这个范围外的情况判断为从未发生。

- 有 2 条 `workbuddy_timeout`，分别约 240582 ms / HTTP 504 和 240592 ms / HTTP 502，均为 Claude Desktop → WorkBuddy 的 Messages 调用。耗时与本地 240 秒总预算吻合；记录没有保留足够细节来独立区分所有 SDK 内部与适配层计时来源。不能再说仅有故障注入测试、没有实际超时记录。
- 该批记录未出现 `upstream_idle_timeout` / `upstream_total_timeout`，也没有明确的 SSE 单行过大错误。不能据此推断更早记录中从未有过。
- 65536 是提前压缩的触发值，自身不是拒绝请求的错误码。去掉后可能减少压缩次数，但容量未知时也可能完全不自动压缩。
- WorkBuddy 60 秒无进展 / 240 秒总预算：前者看模型是否继续产生事件，后者即使仍在工作也会到时取消。去掉可以允许慢请求继续，但 SDK 真挂起时也会等更久，用户仍能取消。此轮没有修改它们。
- SSE 1/50 MiB 是**一条传输数据行**的上限，不是整篇回答或整个对话的长度。长回答可以分成很多小条，通常不会因此触发；一次发送非常大的工具参数、内容块才可能碰上。取消固定行上限需要相应处理内存占用。此轮没有修改解析器。
