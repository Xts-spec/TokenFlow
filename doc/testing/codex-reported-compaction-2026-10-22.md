# Codex 实际续聊故障排查（2026-10-22）

本次读取运行版 10.15.26.52 的活动记录和对应 Codex 会话，修复源码并做隔离回归。没有修改真实会话、账号、Codex 配置或替换正在运行的应用。用户提供的报告和海报对话仅作为故障证据。

## 实际证据

- 报告续聊记录中有 160 次 `compacted` 事件。10:51:34 UTC 的检查点解开后包含 **159 条旧摘要，共 631039 字节**，还携带固定指令和近期工具交互。旧实现永久保留每一条历史摘要、再追加一条新摘要，导致越压缩越积累。这是已确认的网关缺陷。
- 海报续聊的首个请求为 09:04:12 UTC（本地 02:04:12），输入用量 109708 Token、缓存 0、HTTP 200，活动记录没有压缩。第二次输入 110177 Token，也没有压缩。首次压缩始于 09:05:42 UTC，耗时 24.457 秒、调用摘要上游两次。因此这条实际会话不是网关在首轮无条件触发整理；之后的压缩来自 Codex。
- 海报续聊共记录 9 次压缩。当前输入包含指令、工具及历史，不只包含界面可见消息。模型容量未知时现有 Codex 软触发值是 128000 Token；修复摘要累积不代表大的固定上下文不再占用窗口。缓存命中同样属于当前输入，不能从窗口占用中扣除。
- 活动中 Qoder 的 `qoder_capacity_wait_exhausted` 明确指向来源容量不足。旧链路经过嵌套错误封装和重复分类后丢失了这条具体提示。
- 08:59:51 UTC 的 DeepSeek API HTTP 400 没有保留下游可核验的原始错误细节；旧 API relay 会丢弃失败响应正文。无法追溯判定是上下文超限、参数不兼容还是该供应商的其他校验。HTTP 400 本身不足以归因。
- WorkBuddy 摘要错误此前会被统一包装成“上游 502 / 本地 422”。旧记录不够区分实际来源原因，不能把这些 502 都当作 Qoder 容量不足。

## 修复

1. Codex 主动请求远程压缩时，完整旧摘要与新增历史一起交给摘要模型，生成替代摘要，不再永久追加旧摘要。首次返回网关仍优先复用已有摘要、只整理新增历史；持久缓存、固定分组和历史备份保留。
2. 新会话只有固定指令和第一条用户请求时，不产生没有缩减作用的首次整理检查点。这是另一个回归用例确认的问题；不是上述海报会话首轮行为的原因。
3. API relay 保留已识别的错误类别及结构化参数路径；识别多层 JSON 错误封装；WorkBuddy 认证/限流保留稳定代码。远程摘要失败保留实际可识别的 400/401/429 等状态，不再统一改为 422。未知响应继续使用原有脱敏策略。
4. 安装版 Codex 对纯 HTTP 429 的重试错误会隐藏响应正文。实际开始远程压缩后，沿用进度 SSE，将来源具体错误以 `response.failed` 送给 Codex；TokenFlow 活动同时记录原错误状态和提示。没有因此新增压缩触发或等待时限。

摘要响应只返回加密检查点，不把摘要文本当作正常助手回复发送。用户看到压缩之间的“我会先……”属于恢复后的普通模型推理；回归覆盖压缩流不包含 `response.output_text.delta`、后续回复单独进行。

本次没有更改触发阈值、分块大小、并行度、请求时限，也没有增加正文裁剪或拒绝条件。
